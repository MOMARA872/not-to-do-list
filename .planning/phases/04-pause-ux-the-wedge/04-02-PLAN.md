Dart signature (Phase 2 — frozen):
```dart
bool isInScheduleWindow({
  required DateTime now,
  required int? startMinutes,
  required int? endMinutes,
  required int? weekdayMask,
});
```

Semantics (paraphrased from Dart docstring lines 14-31):
- All three nullable ints null → return false (no schedule = dormant)
- localNow = now.toLocal(); nowMinutes = localNow.hour * 60 + localNow.minute
- todayWeekdayBit = 1 << (localNow.weekday - 1)  // Mon=1..Sun=7 → bit 0..6
- Same-day (start <= end): half-open [start, end); active iff nowMinutes in range AND today's weekday bit set
- Cross-midnight (end < start): if nowMinutes >= start, head [start..midnight) — TODAY's weekday bit; if nowMinutes < end, tail [midnight..end) — YESTERDAY's weekday bit (START-day semantics); else false

Kotlin equivalent — chosen signature (matches the Pigeon-style primitive ABI we'll need to call from the service hot path):
```kotlin
fun isInScheduleWindow(
    nowEpochMs: Long,
    startMinutes: Int?,
    endMinutes: Int?,
    weekdayMask: Int?,
    timeZone: java.util.TimeZone = java.util.TimeZone.getDefault()
): Boolean
```

Why epochMs + TimeZone (not java.time.LocalDateTime): the service receives `System.currentTimeMillis()` already; the parity oracle needs to construct identical instants on Dart and Kotlin sides; passing the timezone explicitly makes the test parameterizable (DST and tz-shift tuples become deterministic).
